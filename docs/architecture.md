# Architecture

The host assistant provides conversation, model access and tools. The skill routes requests; role documents specify responsibilities. The local CLI stores graph snapshots, revision counters, transition evidence and current nodes. Node handlers are performed by the host, not dispatched automatically by JavaScript.

Task files live in <project>/.engineering/tasks/<uuid>/task.json. Store briefs, plans, domain assessments, diffs, reviews and validation reports beside that file. Each task embeds its graph and a checksum, so later graph edits do not affect running tasks. The checksum detects accidental changes; it is not an authentication mechanism.

Writes use an exclusive lock and atomic rename. Stale revisions are rejected. Locks contain local host, PID and creation time. A crash can leave a lock: use recover to refuse live writers, back up valid state, and remove a dead local writer lock. Incomplete metadata, foreign-host locks and stale recovery mutexes require manual inspection. Recovery assumes no external process replaces lock files outside this protocol. Atomic rename protects readers, but full power-loss durability is not guaranteed. Local files are trusted input; there is no multi-user security boundary. Do not run task files supplied by untrusted users.

The CLI cannot enforce host command permissions, prove approval authenticity, check arbitrary agent output contracts or prove review quality. These remain host/instruction responsibilities. All edges have traversal budgets, bounding loops. Required-gate checks establish structural reachability constraints, not semantic approval correctness.

Schema v2 adds project root, code snapshots and superseding task links. V1 stays readable. Structured graph evidence checks artifact existence, approval fields, declared code-file snapshots and validation fields; it cannot establish evidence truth. Cancellation is a revision-checked administrative event to an unsuccessful terminal.

The product graph is separate from task state: PRODUCT.json registers feature directories, each feature.json declares scope/policy documents, component edges and test mappings, and PRODUCT.md is a generated index. src/product.js validates declared paths and dependencies, computes change impact and records per-feature versions with content snapshots. V3 task graphs opt into productMap checks. Product metadata belongs in source control; task state can remain local. Source imports, policy semantics, actual test execution and version authenticity remain host responsibilities.

Product schema 2 adds root document references, domains, preparation snapshots and per-feature synchronization records. V4 task graphs require productPreparation before initial implementation. Synchronization binds declared feature/upstream files, shared documents, registry and validation artifacts to documentation/flow/test assessments and passing test records. Generated indexes are checked against the model. These checks do not infer semantic agreement or execute tests. Schema-1 maps remain readable.

V5 graphs opt into engineeringQuality. src/quality.js validates design planning, implementation decision coverage/performance assessment, and engineering review fields. State keeps the current engineering plan and assessment; replan clears them. The runner validates records, not pattern suitability, test/benchmark execution or productivity gains.

V6 opts into criticalPlanning, requiring proposal assessments and design decision analyses. src/quality.js checks recommendation consistency, option comparisons and lifecycle cost fields. Replan replaces the current product assessment and clears the current engineering plan. The runner does not establish estimate accuracy or recommendation quality.

Task schema 3 adds replay validation, event artifact hashes, approval artifact bindings and complete criterion coverage. Implementation also records the project file tree, excluding runtime state, Git metadata and dependencies. Status exposes historical artifact drift. A changed approved artifact prevents entering implementation or passing review/validation until replanning. Files remain trusted local input; this is consistency validation, not authentication.

Product mutations use a write-ahead undo journal for registry, history and index changes, initialization files and newly created feature directories. A failed operation rolls back; if rollback fails, its lock and journal remain for recovery. `product-recover ROOT` refuses a live or foreign-host writer, backs up the undo journal and restores the previous files before releasing a dead writer's lock. The journal is replaced atomically. As with task writes, full power-loss durability across all files and directories is not guaranteed. Incomplete lock metadata and a stale recovery mutex require manual inspection.

Product initialization preflights every target before recording undo entries, including dangling symlinks. Journals preserve symlink targets and regular-file permission modes; rollback restores that metadata along with file contents. Recovery validates the complete undo log before applying it. File snapshots use dictionaries without prototypes so names such as `__proto__` remain ordinary file keys.

Schema-1/2 tasks retain their original artifact resolution, including absolute paths and paths outside the task directory. Schema 3 enforces task-directory containment. Structured graph validation requires evidence-bearing role transitions on every successful route, and initial preparation is checked when entering a worker even through an intermediate node.
